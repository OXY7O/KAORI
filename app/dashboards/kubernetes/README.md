# Kubernetes Dashboard

The Kubernetes Operations Dashboard is a read-only operational projection over committed KAORI data. Web requests must not query Kubernetes, Prometheus, or Alertmanager directly.

## Source contract

- Inventory counts, pod health, node readiness, and resource freshness come from database inventory snapshots.
- Capacity uses `analytics.capacity` with `time_range=24h`.
- Top Consumers uses the current `analytics.top_consumers` committed snapshot; display filters are local.
- Forecast uses `analytics.forecast` with `history_window=30d`; horizon and model are projected locally, while resource navigation remains presentation-only tabs.
- The dashboard Forecast & Growth Risk block renders a compact multi-series line chart: historical utilization is solid, projected utilization is dashed, and warning/critical thresholds remain visible. The same block exposes highest projection, at-risk resource count, forecast horizon, current-to-projected values, and the worker-derived conclusion without issuing a new Prometheus query.
- Consumer insight labels are text-only compact labels; decorative dot icons are not used.
- Alerts use `dashboard.kubernetes.alerts`, generated by the analytics worker from the configured Alertmanager source or Prometheus fallback.
- Reporting and Intelligence sections remain database-backed.
- Missing, pending, failed, stale, or expired worker data is shown explicitly. The web request never falls back to a live integration query.
- Dashboard content cards are always expanded. Section headers are static, and no per-card accordion or expandable state is used; the category tabs remain the only dashboard-level content switcher.

## Request boundary

Protected lazy-section requests enforce `dashboard.view` before resolving the clusterless onboarding state. The clusterless blocker is owned by the permission-protected `section()` view, not a Blueprint `before_request`, because a pre-view response would bypass the view decorator. Unknown section keys return `404` before cluster readiness or dashboard data access.

The initial page request builds only the dashboard shell, inventory aggregate, reporting summary, scope selector, and loading placeholders. Each HTMX section calls `get_dashboard_section()` and loads only the records and committed snapshots needed by that section.

Examples:

- Capacity reads one capacity snapshot and no alert, top-consumer, forecast, or inventory table.
- Top Consumers reads one top-consumer snapshot only.
- Forecast reads one forecast snapshot only.
- Cluster Health uses two set-based inventory queries for the visible clusters, then reads capacity and alert snapshots for those rows.
- Cluster Health reads the API endpoint from the canonical `Cluster.kubernetes_connection.server` relationship; it never reads the removed legacy `Cluster.server` field. Missing binding metadata is presented as `Endpoint unavailable` and does not independently mark the cluster unhealthy.
- KPI cards use database count aggregates rather than hydrating full inventory tables.
- Data Freshness reads database timestamps and snapshot state; it does not execute a health query against an integration.
- Recommended Actions does not hydrate analytics snapshots.

- View models: `schema.py`
- Aggregate and set-based database access: `repository.py`

- Section projection: `sections/`
- Templates: `templates/dashboards/kubernetes/`

## Operational flow

```text
Prometheus / Alertmanager
        ↓ worker execution
AnalyticsSnapshot committed generation
        ↓ database read only
Kubernetes Operations Dashboard
```

The `analytics.materialize` policy includes both dashboard and full-page alert datasets, always retains the dashboard-required 24-hour Capacity snapshot, and materializes one current Top Consumers snapshot per eligible cluster. `analytics.forecast.materialize` always retains the dashboard-required 30-day history; horizon and model are projected locally from that committed history; resource tabs do not alter snapshot identity.

## Styling and workspace composition

The Kubernetes Operations Dashboard is the reference implementation for `docs/design/patterns/OPERATIONAL_DASHBOARD.md` v1.3.

- Hero: `components/page_hero.html`.
- KPI cards: `components/operational_metric_card.html`.
- Peer navigation: **Tab Style 1 — Integrated Workspace Tabs** (`integrated-workspace`) through `components/workspace_tabs.html`; active state is stored in `?tab=`, preserved during HTMX scope changes, and supports Arrow Left/Right, Home, and End keyboard navigation.
- Repeated blocks: `components/operational_section_card.html`.
- Peer main-content layout: `components/peer_content_grid.html`; both boxes stretch to the tallest peer in the row.
- Static action and response flows: `components/operational_flow_steps.html`.
- Visible supporting tips and interpretation: `components/operational_callout.html`.
- `components/context_rail.html` remains reserved for a genuine supporting sidebar, not two peer dashboard boxes.
- Forecast chart: `components/forecast_projection_chart.html`, shared with Kubernetes Analytics.
- Cluster Health: canonical table, semantic labels, shared empty state, and pagination with default 5 and options 5/10/25/50.

Card titles use `text-base font-semibold`. Dashboard metric values follow the documented KPI hierarchy. Ordinary status labels are borderless and semantic; scope and count labels use metadata labels. Page-local tab, chart, card-shell, label, and pagination geometry is prohibited. Dashboard copy must describe committed or detailed signals rather than implying live provider queries, and Reporting guidance must remain artifact-format neutral.

## Alert Source Failure Presentation and Recovery

Dashboard alert snapshots never render raw provider exceptions, endpoint hostnames, query strings, or HTTP client traces. Alert source failures are converted into concise operator guidance, while technical evidence remains in server logs and integration runtime observations.

Celery Beat checks enabled Kubernetes, Prometheus, and Alertmanager integrations through the dedicated runtime queue. When an integration transitions from an unhealthy state back to healthy, KAORI queues focused recovery work: Kubernetes recovery triggers a single-cluster inventory sync, while Prometheus or Alertmanager recovery refreshes the dashboard alert snapshot and the Alerts & Anomalies snapshot for each bound cluster. Recovery dispatch is best-effort and cannot turn a successful runtime health observation into a failure.

### Internal ownership cleanup

The Dashboard owns no compatibility catch-all parameters, orphan Hero integration metadata builder, duplicate byte-format helper, or unused KPI tone API. Internal selected-cluster state is named `selected_cluster`; the term `live` is reserved for actual provider/runtime semantics. User-facing metric and alert copy describes committed worker snapshots rather than implying direct provider queries from the web request.

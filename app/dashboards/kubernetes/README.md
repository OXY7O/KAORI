# Kubernetes Dashboard

The Kubernetes Operations Dashboard is a read-only operational projection over committed KAORI data. Web requests must not query Kubernetes, Prometheus, or Alertmanager directly.

## Source contract

- Inventory counts, pod health, node readiness, and resource freshness come from database inventory snapshots.
- Capacity uses `analytics.capacity` with `time_range=24h`.
- Top Consumers uses the current `analytics.top_consumers` committed snapshot; display filters are local.
- Forecast uses `analytics.forecast` with `history_window=30d`; horizon, resource, and method are projected locally.
- Alerts use `dashboard.kubernetes.alerts`, generated by the analytics worker from the configured Alertmanager source or Prometheus fallback.
- Reporting and Intelligence sections remain database-backed.
- Missing, pending, failed, stale, or expired worker data is shown explicitly. The web request never falls back to a live integration query.

## Request boundary

The initial page request builds only the dashboard shell, inventory aggregate, reporting summary, scope selector, and loading placeholders. Each HTMX section calls `get_dashboard_section()` and loads only the records and committed snapshots needed by that section.

Examples:

- Capacity reads one capacity snapshot and no alert, top-consumer, forecast, or inventory table.
- Top Consumers reads one top-consumer snapshot only.
- Forecast reads one forecast snapshot only.
- Cluster Health uses two set-based inventory queries for the visible clusters, then reads capacity and alert snapshots for those rows.
- KPI cards use database count aggregates rather than hydrating full inventory tables.
- Data Freshness reads database timestamps and snapshot state; it does not execute a health query against an integration.
- Recommended Actions does not hydrate analytics snapshots.

## Technical ownership

- Routes: `routes.py`
- Shell and section orchestration: `service.py`
- Snapshot keys and read contract: `snapshots.py`
- Dashboard alert worker builder: `snapshot_builder.py`
- View models: `schema.py`
- Aggregate and set-based database access: `repository.py`
- Section projection: `sections/`
- Templates: `templates/dashboards/kubernetes/`

## Operational flow

```text
Prometheus / Alertmanager
        ↓ worker execution
AnalyticsSnapshot committed generation
        ↓ database read only
Kubernetes Operations Dashboard
```

The `analytics.materialize` policy includes both dashboard and full-page alert datasets, always retains the dashboard-required 24-hour Capacity snapshot, and materializes one current Top Consumers snapshot per eligible cluster. `analytics.forecast.materialize` always retains the dashboard-required 30-day history; horizon, resource, and method are projected locally from that committed history.

# KAORI VPS deployment

`deploy/vps/` owns KAORI application deployment to the UAT/production-like VPS. It is intentionally separate from `ops/github-runner/`, which owns only GitHub self-hosted runner lifecycle.

`compose.production.yml` remains the canonical KAORI application graph. `deploy/vps/compose.vps.yml` adds VPS-specific PostgreSQL, Redis, Nginx, Certbot, persistent volumes, and deployment/recovery behavior.

## Environment model: local vs production

KAORI deliberately uses two different configuration entry paths so developer convenience does not become production authority.

### Local / Dev Container

Local development keeps the simple developer workflow:

```text
.env.example
    ↓ copy once
.env
    ↓
Dev Container / local Docker Compose
```

Create the local file with:

```bash
cp .env.example .env
```

`.env.example` is the development template. The generated `.env` is local-only and must never be committed.

### Production / VPS

Production uses split configuration by authority:

```text
deploy/env/app.env.example
        ↓
/etc/kaori/app.env


deploy/env/secrets.env.example
        ↓
/etc/kaori/secrets.env


deploy/env/deploy.env.example
        ↓
/etc/kaori/deploy.env

Governed deployment
        ↓
/var/lib/kaori/deploy-state/release.env
```

The four authorities are intentionally different:

| File | Owner | Purpose |
| --- | --- | --- |
| `/etc/kaori/app.env` | operator | Portable KAORI application behavior. No credentials. |
| `/etc/kaori/secrets.env` | operator | Runtime credentials and secret material. |
| `/etc/kaori/deploy.env` | operator | VPS/Compose adapter, immutable dependency images, domain and edge settings. |
| `/var/lib/kaori/deploy-state/release.env` | deployment workflow | Exact application image, version, source SHA and build timestamp after successful verification. |

Do not place `KAORI_IMAGE`, `APP_VERSION`, `APP_BUILD_SHA`, or `APP_BUILD_DATE` in any persistent operator file. Those values are governed release identity and are generated by `deploy.sh`.

## Security and ownership model

- Use the dedicated non-root `kaori-deploy` account for application deployment.
- Docker access is root-equivalent privilege; keep the deploy identity dedicated to KAORI.
- SSH is key-only and uses a passphrase-protected RSA deployment key.
- Only the public deployment key belongs on the VPS. The private key and passphrase stay in the GitHub `uat` Environment secrets.
- `KAORI_VPS_KNOWN_HOSTS` is independently reviewed. Deployment keeps `StrictHostKeyChecking=yes`; there is no learn-and-trust fallback.
- Registry credentials come from GitHub Secrets and are used through an ephemeral Docker configuration directory.
- `app.env`, `secrets.env`, `deploy.env`, `/var/lib/kaori/deploy-state`, and `/var/lib/kaori/backups` are deployment/runtime state and must never be copied into the runner workspace or Actions artifacts.
- PostgreSQL, Redis, and KAORI web do not publish application/state ports on the host. Only the Compose-managed Nginx edge publishes TCP 80 and 443.
- Application and infrastructure images used by UAT/production must be immutable digest-qualified references.

## Temporary UAT runner co-location

During this temporary UAT phase, the self-hosted GitHub runner and KAORI may share the same physical VPS. Physical co-location does not merge their operational ownership.

- Runner identity: `github-runner`, path `/opt/actions-runner`.
- Deployment identity: `kaori-deploy`, path `/opt/kaori`.
- `bootstrap-host.sh` rejects `github-runner` as the KAORI deploy user and preserves `/opt/actions-runner`.
- SSH remains the deployment boundary even when runner and target share the same host. `KAORI_VPS_HOST` must still identify the reviewed VPS endpoint; do not add a localhost/direct-execution shortcut.

Move the runner to a separate host or runner pool when infrastructure capacity permits. The SSH deployment interface should remain unchanged.

## One-time VPS preparation

`deploy/vps/bootstrap-host.sh` prepares the host idempotently. It creates/reuses the deploy user, installs/verifies Docker Engine and the Compose plugin, installs the reviewed RSA public key, creates deployment/state/backup paths, and initializes the three split environment files when they do not already exist.

It does not generate an SSH keypair, change `sshd_config`, or learn an SSH host key.

### 1. Generate the deployment RSA keypair

Run this on the operator workstation, not the VPS:

```bash
ssh-keygen -t rsa -b 4096 -o -a 100 \
  -f ~/.ssh/kaori-uat-deploy \
  -C 'kaori-uat-deploy'
```

Store:

- private key contents in GitHub Environment secret `KAORI_VPS_SSH_PRIVATE_KEY`;
- private-key passphrase in `KAORI_VPS_SSH_PASSPHRASE`;
- only `~/.ssh/kaori-uat-deploy.pub` on the VPS.

### 2. Copy bootstrap material

From an admitted/reviewed KAORI checkout:

```bash
ssh root@<vps-host> 'install -d -m 0700 /root/kaori-bootstrap'

scp \
  ~/.ssh/kaori-uat-deploy.pub \
  deploy/vps/bootstrap-host.sh \
  deploy/env/app.env.example \
  deploy/env/secrets.env.example \
  deploy/env/deploy.env.example \
  root@<vps-host>:/root/kaori-bootstrap/
```

Only repository templates and the public key are copied. Real secret values are created/maintained only on the VPS.

### 3. Run bootstrap

On the VPS as root:

```bash
bash /root/kaori-bootstrap/bootstrap-host.sh \
  --ssh-public-key-file /root/kaori-bootstrap/kaori-uat-deploy.pub \
  --app-env-template /root/kaori-bootstrap/app.env.example \
  --secrets-env-template /root/kaori-bootstrap/secrets.env.example \
  --deploy-env-template /root/kaori-bootstrap/deploy.env.example
```

Defaults:

- deploy user: `kaori-deploy`;
- deploy root: `/opt/kaori`;
- app config: `/etc/kaori/app.env`;
- secrets: `/etc/kaori/secrets.env`;
- deployment adapter: `/etc/kaori/deploy.env`;
- active release identity: `/var/lib/kaori/deploy-state/release.env` after a governed deployment succeeds;
- backups: `/var/lib/kaori/backups`;
- SSH port metadata: `22`.

Bootstrap preserves existing split environment files rather than overwriting them.

### 4. Complete the three production files

Review each file separately:

```bash
sudoedit /etc/kaori/app.env
sudoedit /etc/kaori/secrets.env
sudoedit /etc/kaori/deploy.env
```

Use the templates as the source of truth:

```text
deploy/env/app.env.example
deploy/env/secrets.env.example
deploy/env/deploy.env.example
```

Key ownership rules:

- application behavior, worker settings, report/storage policy, public base URL and trusted hosts → `app.env`;
- `SECRET_KEY`, integration encryption keys, PostgreSQL/Redis passwords, connection URLs, S3 credentials and external provider client secrets → `secrets.env`;
- PostgreSQL/Redis/Nginx/Certbot immutable image references, PostgreSQL database/user, public domain/IP and edge renewal intervals → `deploy.env`;
- application image/version/SHA/build timestamp → never operator-edited; generated in `release.env`.

When using existing PostgreSQL/Redis volumes, preserve the existing database and Redis passwords during migration. Do not rotate them merely because the file layout changed.

### 5. Verify ownership and permissions

```bash
stat -c '%a %U %G %n' \
  /etc/kaori/app.env \
  /etc/kaori/secrets.env \
  /etc/kaori/deploy.env
```

Expected modes:

```text
640 kaori-deploy kaori-deploy /etc/kaori/app.env
600 kaori-deploy kaori-deploy /etc/kaori/secrets.env
640 kaori-deploy kaori-deploy /etc/kaori/deploy.env
```

Then verify deploy-user runtime access:

```bash
sudo -u kaori-deploy docker info
sudo -u kaori-deploy docker compose version
```

Docker Compose `2.24.4` or newer is required because the VPS overlay uses `!reset` and `!override`.

### 6. Pin the VPS SSH host key

Collect a candidate host-key record from a trusted operator machine and verify its fingerprint independently before storing it in GitHub:

```bash
ssh-keyscan -p 22 <vps-host> > kaori-vps.known_hosts.candidate
ssh-keygen -lf kaori-vps.known_hosts.candidate
```

Store only the independently verified record in `KAORI_VPS_KNOWN_HOSTS`.

## Legacy `.env.production` migration

`/etc/kaori/.env.production` is a legacy monolithic configuration source. Do not create a new `/etc/kaori/.env.production`.

For an existing pre-split VPS, use the old file only as a migration source:

1. copy non-secret application behavior into `/etc/kaori/app.env`;
2. copy existing credentials, PostgreSQL/Redis passwords and connection URLs into `/etc/kaori/secrets.env`;
3. copy deployment-specific values into `/etc/kaori/deploy.env`;
4. do not copy application release identity (`KAORI_IMAGE`, `APP_VERSION`, `APP_BUILD_SHA`, `APP_BUILD_DATE`);
5. keep the old file untouched during the first split-environment rollout;
6. retire it only after a governed split-environment deployment passes internal runtime, HTTPS ingress, backup/rollback evidence, and UAT verification.

Do not rotate existing PostgreSQL/Redis passwords as part of this layout-only migration unless password rotation is a separate reviewed change.

## GitHub Environment `uat`

Configure the `uat` Environment with:

Secrets:

- `KAORI_VPS_SSH_PRIVATE_KEY`;
- `KAORI_VPS_SSH_PASSPHRASE`;
- `KAORI_VPS_KNOWN_HOSTS`;
- `KAORI_DOCKER_REGISTRY_USERNAME`;
- `KAORI_DOCKER_REGISTRY_PASSWORD`.

Variables:

- `KAORI_VPS_HOST`;
- `KAORI_VPS_USER` (normally `kaori-deploy`);
- `KAORI_VPS_PORT` (normally `22`);
- `KAORI_VPS_DEPLOY_ROOT` (optional, defaults to `/opt/kaori`);
- `KAORI_LETSENCRYPT_EMAIL`.

When runner and target are co-located, `KAORI_VPS_HOST` still identifies the reviewed VPS endpoint. Do not replace the pinned SSH boundary with `localhost`.

## Intentional RC deployment authority

`.github/workflows/deploy-uat-vps.yml` accepts only governed intentional RC evidence.

Required order:

1. merge reviewed work to `kaori/staging`;
2. wait for exact Full Admission PASS on the staging SHA;
3. cut an intentional RC for that exact SHA;
4. move `kaori/uat-request` to that same admitted staging SHA;
5. let `KAORI UAT VPS Deploy` resolve the matching prerelease and immutable image evidence;
6. deploy through pinned SSH trust.

Before SSH, the workflow verifies the request SHA, current staging SHA, GitHub prerelease/tag SHA, exact Full Admission run, successful publisher run, unexpired artifact, and immutable digest evidence.

Free-form image/SHA deployment is not an authorized UAT path.

## Deployment lifecycle

`deploy/vps/deploy.sh` performs the governed transaction:

1. validate split environment files and their permissions;
2. validate the exact application digest, source SHA, RC version, Docker/Compose capabilities, public domain/IP and immutable infrastructure image pins;
3. authenticate to the registry ephemerally and pull the exact application image;
4. verify the OCI source revision and create a transient candidate release identity;
5. validate Compose using `/etc/kaori/deploy.env`;
6. pull/start immutable PostgreSQL and Redis and wait for health;
7. create a pre-migration PostgreSQL backup when an existing application schema is present;
8. validate portable application configuration;
9. run the one-shot database migration;
10. start KAORI web/workers/Beat using the exact candidate image;
11. verify application containers, queues, single Beat, exact image identity and private application/state ports;
12. start Compose-managed Nginx + Certbot;
13. wait for trusted `https://<domain>/health/ready`;
14. run DNS, redirect, TLS, HSTS, Host/SNI rejection, private-port and renewal verification;
15. only after all checks pass, promote candidate release identity to `/var/lib/kaori/deploy-state/release.env` and record current/previous deployment evidence.

## Compose edge

Public ingress is part of the Compose project, not a separately managed host Nginx installation:

```text
Internet :80/:443
        ↓
Compose Nginx
        ↓
Docker network
        ↓
web:5000
```

Only Nginx publishes host 80/443. KAORI web, PostgreSQL and Redis remain private to the Docker network. See `deploy/nginx/README.md` for ACME/TLS lifecycle and ingress verification details.

Host firewall, SSH daemon, Docker daemon, kernel/networking and provider controls remain host responsibilities.

## Verification

After one governed deployment succeeds:

```bash
bash deploy/vps/verify.sh --restart-check
```

The verifier defaults to:

```text
/etc/kaori/deploy.env
/etc/kaori/app.env
/etc/kaori/secrets.env
/var/lib/kaori/deploy-state/release.env
```

It reloads current release identity from deployment state; operators do not re-enter release version/SHA/image values.

Public ingress verification is performed by the deploy transaction and can also be run from the admitted release checkout:

```bash
bash deploy/nginx/verify-ingress.sh \
  --domain kaori.cloud \
  --expected-ip 62.171.187.206 \
  --renewal-dry-run
```

## Backup and restore

Create a PostgreSQL custom-format backup and checksum:

```bash
bash deploy/vps/backup.sh
```

The backup utility reads `/etc/kaori/deploy.env` by default and recovers current release identity from deployment state.

Restore is fail-closed: the dump must be under `/var/lib/kaori/backups`, have its SHA256 sidecar, and application services are stopped before `pg_restore --exit-on-error` runs.

```bash
bash deploy/vps/restore.sh \
  /var/lib/kaori/backups/kaori-postgres-<timestamp>.dump
```

## Rollback

KAORI refuses image-only rollback when schema state may have changed. A rollback must explicitly restore the recorded pre-migration backup first:

```bash
{
  printf '%s\n' "$REGISTRY_USERNAME"
  printf '%s\n' "$REGISTRY_PASSWORD"
} | bash deploy/vps/rollback.sh --restore-backup
```

Rollback restores the reviewed database recovery point and redeploys the recorded previous immutable image/source/version through the same governed `deploy.sh` path.

## UAT and stable promotion boundary

A successful HTTPS deployment is necessary but does not authorize stable release by itself.

UAT evidence must retain the exact staging SHA, intentional RC tag, immutable application digest, deployment run, database safety evidence, private-port proof, DNS/TLS/renewal evidence and public readiness result. Human UAT must explicitly accept that exact source SHA and digest before Issue #51 may promote `kaori/staging` to `main`.

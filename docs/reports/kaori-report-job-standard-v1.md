# KAORI Report Job Standard v1.0

## Purpose
Every report artifact is generated by the dedicated Reports worker and represented by one canonical `JobExecution`.

## Execution modes
- **Analytics** uses `time_range`. The job payload persists `period`, `window_start`, and `window_end` derived at enqueue time. Supported windows are 24h, 7d, 30d, 90d, and current month.
- **Inventory** uses `committed_snapshot`. The report period is always `snapshot`; the worker resolves the latest committed inventory generation at or before the persisted cutoff.

## Canonical parameters
`contract_version`, `report_id`, `report_type`, `report_family`, `execution_mode`, `selected_cluster_id`, `namespace`, `output_format`, `sections`, `period`, `window_start`, `window_end`, `snapshot_policy`, `trigger_type`, `schedule_id`, `schedule_run_id`, and `requested_at` are stored in `JobExecution.payload_json`.

## Lifecycle
1. Validate selected-cluster and family/format contract.
2. Resolve the immutable evidence boundary.
3. Render and persist the artifact.
4. Commit result reference and delivery state.
5. Mark `JobExecution` terminal and create persistent completion/failure notifications.

Generate Now, recurring schedules, and future API dispatches must call `enqueue_report_generation`; they must not invoke the renderer directly.

## Queues and deduplication
The task `app.reports.jobs.tasks.generate_report_job` runs on the `reports` queue. The resource group is `report:{report_id}`. Analytics jobs use heavy workload admission; inventory jobs use standard admission. Duplicate dispatches attach the requester as a subscriber to the active execution.

## Notification contract
Queued, completed, and failed report events are persistent Notification Center records. Completion notifications include `job_execution_id`, `job_public_id`, `report_id`, `report_type`, output format, and final status. Background report jobs do not create stacked toasts.

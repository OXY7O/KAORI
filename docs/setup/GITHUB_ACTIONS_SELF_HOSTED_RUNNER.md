# GitHub Actions Self-Hosted Runner Setup

This runbook defines the host contract and bootstrap process for a dedicated KAORI GitHub Actions self-hosted runner.

## Scope

This setup prepares the runner host only. It does **not** change KAORI workflow files, register the runner automatically, or install KAORI application runtimes on the host.

The intended boundary is:

```text
Linux host
├── GitHub Actions Runner (systemd)
├── Docker Engine
├── Docker Buildx
└── base host utilities
        │
        └── GitHub Actions jobs
            ├── KAORI CI toolchain container
            ├── PostgreSQL service container
            └── Redis service container
```

Python, Node.js, npm application tooling, PostgreSQL server, Redis server, and KAORI build/runtime dependencies belong in CI containers rather than on the runner host.

## Host Contract

Use a mainstream Linux distribution with:

- `systemd`
- Docker Engine
- Docker Buildx
- `bash`
- `git`
- `curl`
- `tar`
- `gzip`
- CA certificates
- outbound HTTPS access to GitHub

The bootstrap script currently supports package installation through `apt` or `dnf`. The host distribution is intentionally not locked to a specific vendor.

Recommended initial sizing for one KAORI runner instance:

```text
2 vCPU
4 GB RAM
50 GB disk
2 GB swap recommended
```

Use one runner instance initially so KAORI jobs execute one at a time on this VM. This avoids excessive contention on a small runner host.

## Security Boundary

The dedicated runner account is added to the `docker` group. Docker group membership is effectively root-equivalent access to the host.

Treat the VM as dedicated CI infrastructure and run only trusted KAORI workflows. Do not expose this runner to untrusted pull-request code.

Do not store GitHub runner registration tokens, personal access tokens, repository secrets, or application credentials in the bootstrap script.

## Bootstrap

From the KAORI repository root:

```bash
chmod +x scripts/bootstrap_github_runner_host.sh
sudo scripts/bootstrap_github_runner_host.sh
```

The script:

1. Detects Linux architecture and `apt`/`dnf` package family.
2. Installs base host utilities.
3. Installs or verifies Docker Engine.
4. Installs or verifies Docker Buildx.
5. Enables Docker through `systemd`.
6. Creates the dedicated `github-runner` service account.
7. Adds `github-runner` to the `docker` group.
8. Creates `/opt/actions-runner`.
9. Downloads the GitHub Actions Runner binary.
10. Runs the GitHub-provided runner dependency installer.
11. Performs host verification and a Docker smoke test.

The script intentionally stops before GitHub registration.

### Bootstrap options

Show all options:

```bash
scripts/bootstrap_github_runner_host.sh --help
```

Verify an already prepared host without modifying it:

```bash
sudo scripts/bootstrap_github_runner_host.sh --verify-only
```

Prepare only the host and Docker, without downloading the runner binary:

```bash
sudo scripts/bootstrap_github_runner_host.sh --skip-runner-download
```

Skip the Docker `hello-world` smoke test if image pulls are intentionally restricted:

```bash
sudo scripts/bootstrap_github_runner_host.sh --skip-docker-smoke
```

## Manual Runner Registration

Runner registration remains manual by design because GitHub generates a time-limited registration token.

In GitHub, open:

```text
Repository Settings
→ Actions
→ Runners
→ New self-hosted runner
```

Use the registration command generated by GitHub. The target layout is:

```bash
sudo -u github-runner -H bash -lc '
  cd /opt/actions-runner &&
  ./config.sh \
    --url <GITHUB_REPOSITORY_OR_ORGANIZATION_URL> \
    --token <TIME_LIMITED_REGISTRATION_TOKEN> \
    --name <RUNNER_NAME> \
    --labels kaori-ci \
    --unattended
'
```

Do not copy a registration token into repository files or commit history.

After registration, install and start the runner service:

```bash
cd /opt/actions-runner
sudo ./svc.sh install github-runner
sudo ./svc.sh start
sudo ./svc.sh status
```

Expected GitHub runner state:

```text
Online
Idle
```

Expected runner labels include:

```text
self-hosted
linux
x64
kaori-ci
```

Architecture labels depend on the VM architecture.

## Host Verification

Run:

```bash
sudo scripts/bootstrap_github_runner_host.sh --verify-only
```

Also verify Docker as the runner user:

```bash
sudo -u github-runner -H docker info
sudo -u github-runner -H docker buildx version
sudo -u github-runner -H docker run --rm hello-world
```

Check the runner service after registration:

```bash
cd /opt/actions-runner
sudo ./svc.sh status
```

## Local Development Isolation

The local KAORI Dev Container and the GitHub self-hosted runner use different Docker daemons and therefore different networks, volumes, containers, and host ports.

```text
Developer laptop / WSL              CI runner VM
Docker Desktop / local Docker       Docker Engine
└── KAORI Dev Container Compose     └── GitHub Actions job network
    ├── db                              ├── CI toolchain container
    ├── redis                           ├── PostgreSQL service
    └── workers                         └── Redis service
```

KAORI CI service containers should not publish PostgreSQL or Redis ports to the runner host when the job itself runs in a container. The job should address services by service name, for example:

```text
postgres:5432
redis:6379
```

Local development keeps its existing Docker Compose service names and environment contract. CI uses its own environment values. Application code must continue to consume database and Redis endpoints through environment variables rather than hard-coded hostnames.

## Planned CI Architecture

The future KAORI CI design is:

```text
feature branch
    ↓
self-hosted runner
    ↓
static quality gate       ─┐
functional test gate      ├─ containerized CI toolchain
frontend gate             ─┘
    ↓
production image build
    ↓
all required gates pass
    ↓
merge to main
```

The CI toolchain container will provide the controlled Python, Node.js, native PDF/build libraries, and test tooling. PostgreSQL and Redis remain service containers. Production image builds use the host Docker Engine and Buildx rather than Docker-in-Docker.

## Current Repository State

Adding this bootstrap and runbook does **not** switch `.github/workflows/quality.yml` to the self-hosted runner yet.

Do not change `runs-on` or the current CI networking contract until the runner is registered, online, and verified with a dedicated test workflow or controlled migration step.

## Maintenance

Keep the host minimal. Apply normal OS and Docker security updates, monitor free disk space, and remove stale Docker build cache when necessary.

Before upgrading the GitHub Actions Runner, stop the service, follow the upstream runner upgrade procedure, then verify the service and Docker access again.

The long-term source of truth should remain:

```text
Host          = executor only
Containers    = CI build/test environment
Repository    = application dependency/version source of truth
```

# Kubernetes Dashboard Worker Snapshot Boundary

## Decision

The Kubernetes Operations Dashboard is worker-first and database-only. A
Dashboard HTTP request must never instantiate a Prometheus client, Alertmanager
client, analytics service that performs a provider query, or Kubernetes API
client.

## Previous failure mode

The dashboard shell started multiple HTMX requests. Every section rebuilt the
full dashboard context, repeatedly loaded inventory tables, and several sections
executed live integrations. Capacity and Alerts were repeated by KPI and Data
Freshness, while Forecast executed a long-range Prometheus query during page
rendering. Latency and integration timeouts therefore leaked directly into
user-facing response time.

Cluster Health also performed Node and Pod inventory queries per visible
cluster. A five-row page could issue ten inventory queries before capacity and
alert processing.

## Corrected architecture

1. `get_dashboard_overview()` builds only the database-backed shell, inventory
   aggregates, reporting summary, scope selector, and loading placeholders.
2. `get_dashboard_section()` dispatches one focused section builder. A Capacity
   request does not hydrate Alerts, Top Consumers, Forecast, or unrelated
   inventory rows.
3. Capacity, Top Consumers, Forecast, and Alerts read committed
   `AnalyticsSnapshot` payloads.
4. Cluster Health loads Node and Pod inventory for the visible clusters in two
   set-based queries, groups the rows in memory, and joins them with committed
   capacity and alert snapshots.
5. Inventory summary and KPI counts use database aggregate queries instead of
   loading complete inventory tables into the web process.
6. Data Freshness reads inventory timestamps and snapshot metadata only. It
   never validates integrations by executing analytics queries.
7. Missing snapshots produce explicit unavailable, pending, failed, stale, or
   expired presentation. There is no live fallback.
8. Dashboard and full-page alert datasets are generated by
   `analytics.materialize` through the existing analytics snapshot model; no
   schema migration is required.
9. Dataset keys and the dashboard-alert context builder are owned by
   `app.analytics.materialization`. Dashboard modules import only the read contract; Analytics never
   imports Dashboard implementation modules.
10. Integration recovery dispatches refreshes through registered Job Registry definitions. It does
    not import Inventory, Governance, or Analytics job implementations directly.

## Dataset contract

| Dashboard signal | Dataset | Canonical parameters |
|---|---|---|
| Capacity | `analytics.capacity` | `cluster_id`, `time_range=24h` |
| Top Consumers | `analytics.top_consumers` | `cluster_id` |
| Forecast | `analytics.forecast` | `cluster_id`, `history_window=30d` |
| Alerts | `dashboard.kubernetes.alerts` | `cluster_id` |

The Analytics policy always retains the dashboard-required `24h` Capacity
snapshot. Top Consumers uses one current cluster snapshot. Forecast
materialization always retains `30d` historical input because that history is
consumed by the dashboard. Forecast horizon and model are projected locally.
Resource tabs are presentation-only and do not produce separate provider queries or snapshot fingerprints.

Alertmanager-only clusters are eligible for both
`dashboard.kubernetes.alerts` and `analytics.alerts`. Prometheus-backed datasets
remain restricted to clusters whose binding and technical capability contracts
are eligible.

## Request and execution boundary

```text
Browser request
  ├─ shell: database aggregate and report summary
  └─ HTMX section
       ├─ focused inventory aggregate or set query
       └─ committed AnalyticsSnapshot read

Analytics / Forecast worker
  ├─ Prometheus or Thanos query
  ├─ Alertmanager or Prometheus alert fallback
  └─ atomic AnalyticsSnapshot commit
```

The web process may decode and project a committed snapshot. It must not
generate one inline.

## Deployment

No migration or new environment variable is required. Deploy web, Beat,
analytics worker, and forecasting worker from the same release. Run one
Analytics Data Refresh and one Forecast Data Refresh after deployment so every
eligible cluster has the parameter sets consumed by the dashboard.

When `JOB_MAX_HEAVY_PER_USER=1`, wait for Analytics Data Refresh to reach a
terminal state before starting Forecast Data Refresh. A quota rejection is an
expected warning and must not be logged as an infrastructure exception.

## Validation

Run:

```bash
pytest -q \
  tests/analytics/test_kubernetes_analytics_materialization.py \
  tests/dashboards/test_kubernetes_dashboard_snapshot_flow.py
python scripts/verify_python_syntax.py
```

Then verify:

- `/dashboards/kubernetes/section/*` requests complete without outbound
  Prometheus or Alertmanager calls in web logs;
- analytics worker logs own Capacity, Top Consumers, and both alert dataset
  generations;
- forecasting worker logs own Forecast history generation;
- Cluster Health performs set-based Node and Pod reads for the visible page;
- missing snapshots render worker-snapshot states instead of starting a live
  query; and
- Forecast horizon, model, and active resource-tab changes do not dispatch a worker job.

## Rollback

Rollback the application commit and restart web, Beat, analytics worker, and
forecasting worker. Existing `AnalyticsSnapshot` rows are schema-compatible.
Rows created with canonical parameter fingerprints can remain; older readers
will ignore dataset or parameter combinations they do not request.

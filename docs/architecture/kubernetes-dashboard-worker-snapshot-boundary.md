# Kubernetes Dashboard Worker Snapshot Boundary

## Decision

The Kubernetes Operations Dashboard is worker-first and database-only. A dashboard HTTP request must never instantiate a Prometheus client, Alertmanager client, analytics service that performs a live query, or Kubernetes API client.

## Previous failure mode

The dashboard shell started eight HTMX requests. Every section rebuilt the full dashboard context, repeatedly loaded inventory tables, and several sections executed live integrations. Capacity and Alerts were repeated by KPI and Data Freshness, while Forecast executed a long-range Prometheus query during page rendering. Latency and integration timeouts therefore leaked directly into user-facing response time.

Cluster Health also performed Node and Pod inventory queries per visible cluster. In a five-row page this produced ten inventory queries before capacity and alert processing.

## Corrected architecture

1. `get_dashboard_overview()` builds only the database-backed shell, inventory aggregate, reporting summary, scope selector, and loading placeholders.
2. `get_dashboard_section()` dispatches one focused section builder. A Capacity request does not hydrate Alerts, Top Consumers, Forecast, or inventory rows.
3. Capacity, Top Consumers, Forecast, and Alerts read `AnalyticsSnapshot` committed payloads.
4. Cluster Health loads Node and Pod inventory for the five visible clusters in two set-based queries, groups the rows in memory, and joins them with committed capacity and alert snapshots.
5. Inventory summary and KPI counts use database aggregate queries instead of loading complete inventory tables into the web process.
6. Data Freshness reads inventory timestamps and snapshot metadata only. It never validates integrations by executing analytics queries.
7. Missing snapshots produce explicit unavailable, pending, failed, stale, or expired presentation. There is no live fallback.
8. `dashboard.kubernetes.alerts` is generated by `analytics.materialize` and stored through the existing analytics snapshot model; no schema migration is required.

## Dataset contract

| Dashboard signal | Dataset | Parameters |
|---|---|---|
| Capacity | `analytics.capacity` | `cluster_id`, `time_range=24h` |
| Top Consumers | `analytics.top_consumers` | `cluster_id`, `time_range=24h` |
| Forecast | `analytics.forecast` | `cluster_id`, `history_window=30d`, `forecast_horizon=90d`, `resource=all`, `method=linear` |
| Alerts | `dashboard.kubernetes.alerts` | `cluster_id` |

The dashboard-required `24h` Capacity and Top Consumers parameter sets are always retained by Analytics materialization. Forecast materialization always retains the `30d/90d/all/linear` pair. Other ranges remain operator-configurable.

Alert-only clusters are eligible only for `dashboard.kubernetes.alerts`. Prometheus-backed analytics datasets remain restricted to clusters with an eligible Prometheus binding.

## Request and execution boundary

```text
Browser request
  ├─ shell: database aggregate and report summary
  └─ HTMX section
       ├─ focused inventory aggregate or set query
       └─ committed AnalyticsSnapshot read

Analytics / Forecast worker
  ├─ Prometheus or Thanos query
  ├─ Alertmanager or Prometheus alert fallback
  └─ atomic AnalyticsSnapshot commit
```

The web process may decode a committed snapshot. It must not generate one inline.

## Deployment

No migration or new environment variable is required. Deploy web, beat, analytics worker, and forecasting worker from the same release. Run one Analytics Data Refresh and one Forecast Data Refresh after deployment so every eligible cluster has the parameter sets consumed by the dashboard.

## Validation

Run:

```bash
pytest -q tests/dashboards/test_kubernetes_dashboard_snapshot_flow.py
python scripts/verify_python_syntax.py
```

Then verify:

- `/dashboards/kubernetes/section/*` requests complete without outbound Prometheus or Alertmanager calls in web logs.
- Analytics worker logs own Capacity, Top Consumers, and dashboard Alerts generation.
- Forecasting worker logs own Forecast generation.
- Cluster Health performs set-based Node and Pod reads for the visible page rather than per-cluster inventory queries.
- Missing snapshots render a worker-snapshot state instead of starting a live query.

## Rollback

Rollback the application commit and restart web, beat, analytics worker, and forecasting worker. Existing `AnalyticsSnapshot` rows are compatible and do not need removal. Rows with `dataset_key='dashboard.kubernetes.alerts'` may remain because they do not change schema or affect older readers.

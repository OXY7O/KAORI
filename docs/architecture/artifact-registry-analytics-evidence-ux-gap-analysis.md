# Artifact Registry Analytics — Evidence and UX Gap Analysis

**Status:** Source-level implementation audit / Human Visual UAT candidate (2026-11-13)  
**Authority:** Approved Registry architecture `app/templates/artifact_registry/analytics.html` and `app/artifact_registry/{analytics.py,analytics_history.py,presentation_analytics.py}`; #899 (Analytics), #1105/#1122 (cross-domain Analytics), #1097 (navigation), #952 (Alerts), and #900 (central Intelligence).  
**Audience:** KAORI operators, reviewers, and domain implementers.

## Executive finding

Artifact Registry already exposes **Overview + seven focused level-3 routes**: Growth, Capacity, Usage, Risk, Governance, Alerts & Anomalies, and Insights. Normal GETs render a fast committed-state shell and lazy active section. A single ~395-line `_analytics_section.html` owns all seven detailed sections, whereas Kubernetes Analytics splits workspaces among several domain directories and Object Storage Analytics has separate domain partials (Capacity, Performance, Forecast, Top Consumers, Alerts, etc.). This establishes a **presentation/depth gap**, **not a missing-router finding**.

Current worker code also provides real **conditional historical Metrics Source range collection**: `analytics.py::materialize_registry_analytics` uses `collect_registry_metric_history(...)` for non-`current` windows; `analytics_history.py` issues bounded `MetricsConsumer.query_range` calls, classifying `ready/partial/unavailable` with capability/retention gaps. Thus it is **incorrect** to claim all Registry windows merely filter a current snapshot by generated age. The historical #1108 issue describes an earlier baseline; actual provider range readiness and UAT results must still be verified. Current/legacy `current` remains instant evidence, not a historical curve.

In the operator screenshot, **Stale Snapshot**, **0/1 Current** and **Artifact Growth N/A** show that the selected committed evidence is expired or unavailable for this view. They do **not** establish whether the upstream Metrics Source binding is broken, history retention is insufficient, a worker has failed, or the provider simply lacks suitable series. Inspect authoritative source capability, JobExecution status, `time_range` and committed snapshot errors before assigning cause.

## Shared evidence readiness gates — implement before presentation escalation

1. **Source and scope** — Registry integration enabled/active, source capability and binding qualified; worker-held provider/metrics reads only. Selection of All Registries must never imply all providers have usable history.
2. **Generation and freshness** — distinguish eligible/registered, materialized, valid/current, stale-but-readable, failed refresh, partial, unavailable, and unknown. `RegistryAnalyticsSnapshot.status=ready` without valid payload and timestamps is not Current.
3. **Historical evidence** — for measured `1h/6h/12h/24h/7d/30d/60d`, preserve interval, series coverage, source/retention, error reasons, and bounded query sampling; missing measured series is **N/A/Unavailable**, not zero growth, healthy forecast, or a fabricated chart.
4. **Cross-domain joins** — correlate Registry inventory with committed Security, Kubernetes Runtime, Governance and Alert evidence by canonical asset/digest identity and committed generation. Mutable tags have lower confidence. Never turn unsupported or not-collected governance into policy violations.
5. **Action boundary** — Analytics calculates factual review candidates. Intelligence owns Rule Catalog/Recommendations/Accepted Risk; Alertmanager owns alert state; Metrics Source owns metric history; Registry providers own artifact/policy/security observations. No autonomous cleanup or duplicated provider engine.

### Cross-domain presentation difference

The approved cross-domain shell, source selector, ready/snapshot cards, section loader, level-3 navigation, Violet tokens and responsive contract are already reused (#1097, #1099, #1122). The remaining difference is the **domain's analytical body**, not its global page chrome: Registry renders most sections inside one conditional partial with simple metric/card lists and limited evidence inspectors. Kubernetes Analytics has dedicated workload, utilization, storage, capacity, alerts and forecast paths; Object Storage separates Forecast, Capacity, Performance, Top Consumers, Alerts, and evidence-context partials. Avoid cloning their providers or manufacturing plots; reuse only shared information architecture, chart/table/empty-state primitives, and evidence interpretation where actual Registry data supports it.
